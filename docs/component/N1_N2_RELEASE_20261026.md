# rotation_vertical＋N1＋N2 器件方案

团队入口 `tools/run_team_pipeline.py` 现在通过 Component 自有注册表选择：

- Text：`recovery_rotation_vertical_v1`，合并 mobile greedy/beam、server OCR 和 90/270 度竖排候选。
- Component：`rotation_vertical_n1_n2_v1`，YOLO11m、局部 PARSeq、固定 P01 与已观测候选恢复，随后恢复过滤前已有的供电符号，并按图像 OCR 补齐空的电源标签 value。

所有恢复均在引脚和网络推理之前执行。N1/N2 的函数、阈值及赋值顺序来自已验证的提交包，没有重新训练或按错误案例调参。已有非空电源 value 保留；一个物理 OCR 文字组最多分配给一个符号，芯片框内文字不能被邻近电源符号使用。

`pcb/component/recovery/` 将提交包中的独立适配层和所需纯计算函数收进 Component 模块。除了模块导入位置、标准入口缺省缓存路径以及 Windows CUDA DLL 初始化，算法和规则未变。旧 `ordered_yolo11m_local_parseq_v1`、P01 和所有既有注册仍可选择；之前默认器件片段保存在 `configs/component/pre_n1n2.json`。

本次 Git 改动只切换器件配置。仓库既有 L39 Pin、Wire、网络和拓扑配置及代码保持原样。独立完整提交 ZIP 沿用的是 L45＋T；因此 Git 标准默认组合与该 ZIP 的下游选择有区别，不能直接比较两者总分。

## 模型与运行

新增 `models/component/ocr_v5_server/` 中两份 ONNX，使用 Git LFS；其余 YOLO11m、PARSeq、mobile OCR 模型继续使用已有文件。Server 模型在加载时按固定 SHA-256 检查，参数见该目录 manifest。此提交不包含数据集、预测缓存、虚拟环境或 Docker 大 ZIP。

```powershell
git lfs pull
python -m pip install -r requirements.txt
python tools/run_team_pipeline.py --image D:/allowed_images/example.png --output runs/n1n2_example --device cuda --ocr-device cuda
```

GPU OCR 需要兼容的 GPU 版 ONNX Runtime；本地联调用已有 `onnxruntime-gpu 1.23.2`。仅安装 requirements 中的 CPU ONNX Runtime 不能提供 CUDAExecutionProvider。测试环境沿用提交包的 RapidOCR 3.9.2、timm 0.9.16 和本机 Windows CUDA PyTorch；这不等于完成新的 Linux 容器验证。
