# PP-OCRv5 输入归一化与 CTC 多候选解码

范围：仅 Component，不训练、不更换权重，不修改 Pin、Wire、Net 或原评分器。

## 对照设计

使用 `ComponentStageOrderedValues`（当前 `ordered_value_groups_v2`）和同一 YOLO 权重、切块、匹配流程。

| 实验 | 检测输入均值 / 标准差 | 识别解码 |
|---|---|---|
| baseline | 三通道均为 0.5 / 0.5 | 原始贪心 CTC |
| normalization | 官方 v5 的 ImageNet 均值 / 标准差 | 原始贪心 CTC |
| beam | 三通道均为 0.5 / 0.5 | CTC prefix beam + 弱格式先验 |
| combined | 官方 v5 的 ImageNet 均值 / 标准差 | CTC prefix beam + 弱格式先验 |

官方配置出处：[PP-OCRv5_mobile_det.yml](https://github.com/PaddlePaddle/PaddleOCR/blob/main/configs/det/PP-OCRv5/PP-OCRv5_mobile_det.yml)。
mean 为 `[0.485, 0.456, 0.406]`，std 为 `[0.229, 0.224, 0.225]`。本次保持所有尺寸、检测后处理阈值不变，只改变归一化，避免混入其他因素。

每种归一化只运行一遍神经网络，使用同一份概率张量同时得到 greedy 和 beam。分别去重后，各自完整重跑 Component 文字匹配。OCR 改变位号后允许 Component 身份变化，器件 YOLO 不变。

## 多候选解码

- CTC prefix beam 分别累计以 blank / nonblank 结束的路径概率，正确处理连续重复字符。
- beam width=8，每时间步保留 top-6 字符并始终保留 blank；没有篡改识别模型的字符字典。
- 最后用完整概率张量重新计算每条候选文本的 CTC 序列概率，避免仅比较最优单条路径。
- 仅对置信度低于 0.95、长度 2–24 的 ASCII/电气单位文本启用；其他文本保留原读数。
- 位号与数值使用公开通用格式，最多提供 `log(1.5)` 的先验；不使用实际案例的词表或 GT。位号不能通过先验变换器件前缀。
- 候选视觉对数概率相对原读数最多下降 0.7；低于输出置信度 0.5 时退回原读数。
- 保留候选概率、替换文本及原因用于审计。RapidOCR 按宽度重排、再还原裁剪顺序后的读数，通过原文本与精确置信度配对；发生键歧义时保留原读数。

## 数据与评分

入口 `tools/evaluate_component_ocr_ablation.py` 默认白名单为 `0001`–`0150`；调用共享严格选择器逐个校验这 150 个确切目录，拒绝保留编号、重复、缺失、重定向。日志及 manifest 写出实际案例编号。

所有案例四组预测保存并计算 SHA256 后，才允许读取标注。只调用 `evaluate_v2` 的 Component 原语，不构造完整 Pipeline、不运行引脚或网络评分。评分是本地非官方代理，不能当作平台分数。

本轮只运行这一套固定配置，不根据评分继续搜索阈值。默认启用的条件在读取 GT 前固定：全部 150 例的 macro 与 micro F1 均改善，并在既有 train120 / check30 两组中没有 macro 或 micro 回退；满足条件的候选按 train120 macro 选择，并检查推理代价。未满足时保留默认与可选实验版本。check30 仍属于允许开发的前 150 例，不是 0151–0200 保留集。

正式四组使用相同 CUDA 执行设备。缓存签名包含模型校验和、归一化、beam 配置、运行库配置和源码校验和、ORT/NumPy 版本及设备。0001 上的额外 CPU 检查确认成对入口的 greedy 与原程序无缓存重算结果完全一致（622 个 token）；历史旧缓存有 621 个 token，因此不能拿旧缓存直接证明新入口是否等价。CUDA 与 CPU 结果仍可能有浮点差异，正式报告另外保留历史缓存的对照记录。

## 结果

正式结果目录：`runs/component_ocr_ablation_dev150_20261016/`。

| 实验 | 150例 macro ComponentF1 | micro F1 | TP | 提升 / 退步案例 |
|---|---:|---:|---:|---:|
| 当前同环境重算基线 | 0.413105 | 0.416702 | 2450 | — |
| 只改归一化 | 0.406335 | 0.411600 | 2420 | 21 / 42 |
| 只加多候选解码 | **0.414710** | **0.418233** | **2459** | **8 / 0** |
| 归一化＋多候选 | 0.406286 | 0.411770 | 2421 | 21 / 41 |

四组预测器件总数均为 5679，GT 为 6080。多候选增加 9 个完整正确匹配，macro 提高 0.001604（0.1604 个百分点）。这是小幅收益，不能推断平台会有同等涨幅。

| 内部划分 | 基线 macro / micro | 多候选 macro / micro | TP 变化 |
|---|---:|---:|---:|
| train120 | 0.414361 / 0.419013 | 0.415856 / 0.420084 | 1957 → 1962 |
| check30 | 0.408082 / 0.407775 | 0.410125 / 0.411084 | 493 → 497 |

结论：**启用 `ppocrv5_beam`，保留原归一化。** `ordered_value_groups_v2`、YOLO、权重和其他模块配置不变。归一化差异不能仅凭官方配置判定为必须修正，本次实测它在我们的完整识别与匹配链路中降低分数，因此不启用。

正式运行耗时约 31.2 分钟，包含两种归一化网络推理和四组 Component 匹配，不是单个部署版本耗时。600 份预测在 GT 读取前封存，评分前后校验和一致；读取 GT 共 150 次。GPU 为 RTX 3060 Laptop 6GB，ORT 1.23.2。

额外耗时对照（`runs/component_ocr_beam_timing_20261016/`）使用 0001、0002、0003，相同会话、精确图片形状预热、交替测量顺序，禁止消费 OCR 缓存。原解码合计 18.277 秒，多候选 28.542 秒，约增加 **56.2% OCR 耗时**；逐图倍率 1.26–1.97。三张的成对 greedy 输出均与原解码完全一致。这个倍率不代表完整程序耗时，也不是全部 150 例的速度统计。

CPU 追加检查仅使用允许开发的 0024（`runs/component_ocr_ablation_cpu24_20261016/`）：基线 TP=1，多候选 TP=2；这是设备不同后单独重算的结果，不混入 150 例 GPU 汇总。当前默认注册入口的 CPU 冒烟输出与该 CPU beam 预测完全一致，过程中不读 GT（`runs/component_ocr_default_smoke_20261016/`）。

部署整理仅增加了 CUDA 回退后重试仍须报错的保护，以及归一化单项版本跳过不需要的 beam 计算；没有修改已评分的 beam 概率算法或参数。

回切旧版可将 `configs/component/current.json` 的 `text` 设回 `ppocrv5_mobile`。另外两个归一化版本保留为可选实验入口。

## 工程检查

- Component 自身测试 52 项、既有 `test_component_v4` 21 项通过。
- 默认配置契约测试同步 Component/Text 选择；同时修正其此前仍要求 `contextual_values_v2` 的旧断言。该契约目录 22 项通过，其他模块配置与断言不变。
- 按独立子进程分组执行的维护中无数据集测试合计 330 项通过；没有运行其他模块的数据集评分。
- 原 `tools/run_team_tests.py` 在收集空的 `tests/wire` 目录时因目录不可导入而停止；本次使用独立子进程按目录运行其余测试，避免不同目录的同名 `test_legacy` 模块冲突。`wire` 目录无测试。
- 新注册保留原 `ppocrv5_mobile`，新增 `ppocrv5_v5norm`、`ppocrv5_beam`、`ppocrv5_v5norm_beam`，没有覆盖其他模块版本。
